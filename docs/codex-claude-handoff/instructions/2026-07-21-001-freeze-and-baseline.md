# 작업 001: 운영 기준선 동결 및 리빌드 준비

## 배경

현재 고객 화면과 관리자 화면은 거대한 단일 HTML에 다수의 후속 패치가 누적된 구조다. 최근 100개 커밋 중 82개가 `denn-mockup-tool.html`에 집중됐고, 로컬 로드 기준 고객 화면 110개·관리자 화면 123개의 스크립트가 실행된다. 저장 상태도 localStorage, IndexedDB, Firebase Storage, Firestore에 분산돼 있다.

따라서 기존 파일을 대규모 정리하는 작업보다 운영본을 보존하고 현재 동작을 명세·검증하면서 새 구조로 점진 이전한다.

## 목표

1. 현재 운영 소스와 배포 상태를 복구 가능한 기준선으로 고정한다.
2. 리빌드 작업이 기존 운영 파일에 섞이지 않도록 경계를 만든다.
3. 이후 기능별 명세와 회귀 검증을 수행할 수 있는 기반을 마련한다.

## Claude Code 작업 범위

### 1. 먼저 작업 트리 확인

- `git status --short --branch` 확인
- 사용자 변경과 자동 생성 부산물을 구분
- Codex의 이전 분석 과정에서 갱신된 아래 두 파일은 사용자 변경이 없음을 확인한 뒤 `HEAD` 상태로 복원
  - `docs/hot-functions-2026-05-17.md`
  - `docs/patch-inventory-2026-05-17.md`
- 이 전달 폴더의 신규 문서는 보존

### 2. 운영 기준선 보존안 제시

실제 태그·브랜치 생성 전에 사용자에게 다음을 보고하고 승인을 받는다.

- 현재 HEAD와 origin/main 일치 여부
- 실제 프로덕션이 어느 커밋인지 확인 가능한 근거
- 추천 태그 이름
- 추천 리빌드 브랜치 이름(`codex/` 접두사는 사용하지 않아도 되며 사용자·Claude Code 운영 규칙에 맞춘다)
- 롤백 절차

프로덕션 커밋이 불명확하면 추정으로 태그하지 않는다.

### 3. 리빌드 골격 제안

아직 기능 구현을 시작하지 말고 다음 경계만 설계해 사용자에게 제안한다.

- 데이터 모델과 마이그레이션
- 저장소 인터페이스(local/IndexedDB/Firebase)
- 관리자 상태 로딩·저장·게시
- 고객 화면 상태 로더
- 케이스 렌더러
- 액자 렌더러
- 모바일 방 및 전체화면 상태 머신
- 템플릿 편집
- 고객 시안과 주문

기존 HTML 전체를 새 프로젝트에 복사한 후 정리하는 방식은 금지한다. 검증된 기능과 데이터 계약만 순차적으로 옮긴다.

## 이번 작업에서 금지

- 기존 HTML 기능 수정
- 죽은 코드 삭제
- Firebase Rules 변경 또는 배포
- 운영 데이터 읽기·쓰기·마이그레이션
- 프로덕션 배포
- 원인이 확인되지 않은 버그 패치

## 완료 조건

- 작업 트리가 의도한 파일만 변경된 상태
- 운영 기준선 보존안과 롤백 절차가 문서화됨
- 리빌드 디렉터리·기술 선택은 사용자 승인 전 생성하지 않음
- 다음 작업으로 데이터 계약 조사 범위를 제시함
