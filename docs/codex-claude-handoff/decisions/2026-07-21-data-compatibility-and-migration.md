# 결정: 데이터 호환 및 마이그레이션 정책

결정일: 2026-07-21

상태: **확정 · 데이터 작업의 필수 계약**

적용 대상: 신규 리빌드의 데이터 모델, 저장소, Firebase 연동, import/export, 기존 데이터 변환 및 운영 전환

## 핵심 결정

> **기존 원본 데이터 불변 + 신버전 초기 읽기 전용 + 별도 개발 저장 경로 + 사용자 승인된 일회성 운영 전환**

## 1. 운영 원칙

- 기존 운영 데이터를 직접 변형하지 않는다.
- 신버전 초기 단계는 기존 운영 데이터를 읽기만 한다.
- 신버전 저장은 별도 테스트 데이터 또는 별도 개발 경로를 사용한다.
- 구버전과 신버전이 같은 운영 데이터를 동시에 쓰지 않는다.
- 마이그레이션은 페이지 로드나 앱 시작 시 자동 실행하지 않는다.
- 실제 마이그레이션과 운영 쓰기는 사용자 승인 후 별도 작업으로 수행한다.
- 읽기·변환 실패를 기본값으로 덮어써서 정상처럼 진행하지 않는다.

## 2. 데이터 버전 계약

신버전 영속 데이터에는 명시적인 스키마 버전을 포함한다.

```ts
type VersionedDocument<T> = {
  schemaVersion: number;
  migratedAt?: string;
  migratedFrom?: "legacy-v0" | string;
  data: T;
};
```

- 버전 필드가 없는 기존 데이터는 `legacy-v0`로 취급한다.
- 신버전 내부에서는 검증과 마이그레이션을 통과한 최신 스키마만 사용한다.
- 화면·컴포넌트·렌더러에서 과거 필드를 개별 보정하지 않는다.
- 중앙 스키마·마이그레이션 모듈만 데이터 버전을 변환할 수 있다.
- 필드 폐기 후에도 정해진 호환 기간 동안 읽기 변환을 유지한다.

## 3. 마이그레이션 절차

모든 마이그레이션은 다음 단계를 순서대로 수행한다.

```text
원본 읽기
→ 원본 스키마와 무결성 검사
→ 메모리에서 순수 변환
→ 변환 전후 비교 보고서
→ dry-run 검증
→ 별도 개발 위치에 시험 저장
→ 신버전 로드·렌더·저장 검증
→ 사용자 승인
→ 운영 전환 작업
```

단계를 생략하거나 앱 초기화 과정에 숨겨 실행하지 않는다.

## 4. 안전장치

- 운영 변환 전 복구 가능한 원본 백업을 만든다.
- 마이그레이션은 원본을 수정하거나 삭제하지 않는다.
- 같은 입력에 반복 실행해도 같은 결과가 나오는 멱등성을 보장한다.
- 일부 실패를 전체 성공으로 표시하지 않는다.
- 누락, 변환 실패, 알 수 없는 필드를 항목별로 보고한다.
- 변환 전후의 항목 수, 실패 수, 데이터 크기, 이미지 참조 수를 비교한다.
- 검증되지 않은 필드는 조용히 버리지 않고 격리하거나 실패 처리한다.
- Firebase 운영 쓰기는 별도 사용자 승인이 있어야 한다.
- 롤백은 기존 운영본과 원본 데이터를 그대로 다시 사용할 수 있어야 한다.

## 5. 이미지·대용량 데이터

- 기존 `dataUrl`과 `storagePath` 형식을 모두 읽을 수 있어야 한다.
- 변환 중 base64 원본을 자동 삭제하지 않는다.
- Storage 업로드 성공, 다운로드, CORS-clean Canvas 사용을 검증한 후에만 새 URL을 채택한다.
- 마이그레이션을 이유로 기존 Storage 파일을 자동 삭제하지 않는다.
- 신버전은 localStorage에 신규 base64 이미지를 저장하지 않는다.
- 이미지 변환 결과에는 원본 참조와 새 참조의 대응 정보를 남긴다.
- 대형 데이터는 localStorage가 아닌 승인된 IndexedDB 또는 Storage 저장소를 사용한다.

## 6. 구버전·신버전 동시 운영

초기 병행 기간의 권한은 다음과 같다.

```text
구버전: 기존 운영 데이터 읽기·쓰기
신버전: 기존 운영 데이터 읽기
        별도 개발 데이터에만 쓰기
```

신버전이 검증되고 사용자가 cutover를 승인한 이후에만 권한을 전환한다.

```text
구버전: 읽기 전용 또는 운영 종료
신버전: 운영 데이터 쓰기 권한 획득
```

- 동일 운영 문서에 양쪽 앱이 동시에 쓰는 기간을 만들지 않는다.
- 쓰기 권한 전환은 별도 cutover 스펙과 배포·롤백 정책을 따른다.
- cutover 실패 시 신버전 쓰기를 중지하고 구버전 운영으로 복귀한다.

## 7. 필수 호환 대상

최소 다음 입력과 계약을 fixture 및 통합 테스트 대상으로 유지한다.

- `backup.json`
- localStorage `denn_admin`
- IndexedDB `denn_admin_state`
- Firebase `admin/state.json`
- Firebase `published/state.json`
- 기존 `S` / `ADM` 데이터 구조
- `roomBackgroundSettings`의 기존 flat 및 후속 형태
- 템플릿의 `dataUrl` / `storagePath`
- 기존 `?space=<token>` 시안과 `space-scene-v1`
- 기존 주문 IndexedDB 데이터
- 리비전 필드 `__opRev`, `__cloudRev`, `__publishedAt`

## 8. 검증 요구사항

데이터 관련 스펙은 최소 다음 테스트를 포함한다.

- legacy fixture 파싱
- 잘못된 데이터 거부 또는 격리
- 버전별 순차 마이그레이션
- 마이그레이션 멱등성
- 원본 객체 불변성
- 변환 전후 항목 수와 참조 무결성
- 이미지 URL과 CORS 사용 가능성
- 기존 `?space=` 복호화 라운드트립
- 저장 실패와 부분 실패 보고
- dry-run이 외부 상태를 변경하지 않는다는 검증

## 9. 금지 사항

- 앱 시작 시 무승인 운영 데이터 변환
- 기본값으로 운영 데이터를 덮어쓰기
- 구버전·신버전의 동일 운영 데이터 동시 쓰기
- 컴포넌트별 임시 호환 코드
- 업로드 성공만 확인하고 원본 삭제
- 버전 없는 데이터의 암묵적 최신 버전 취급
- 실패 항목을 버리고 전체 성공 반환
- 테스트 데이터와 운영 데이터 경로 혼용

## 10. 승인 조건

데이터 마이그레이션 구현은 다음이 모두 충족돼야 승인할 수 있다.

1. 입력·출력 스키마와 버전이 문서화됨
2. 원본 불변과 멱등성이 테스트됨
3. dry-run 보고서가 제공됨
4. 별도 개발 저장 위치에서 E2E 검증됨
5. 백업과 롤백 절차가 검증됨
6. 사용자에게 실제 쓰기 대상과 영향이 고지됨
7. 사용자가 운영 쓰기를 명시적으로 승인함

## Claude Code 반영 지시

Claude Code는 이 결정서를 `CLAUDE.md`의 강제 데이터 규칙으로 참조한다. 데이터 모델 및 저장소 스캐폴드부터 본 정책을 적용하고, 사용자 승인 없이 운영 데이터 쓰기·변환·삭제를 수행하지 않는다.
