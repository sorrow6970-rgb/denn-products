# 결정: 신버전 변경 및 패치 누적 방지 정책

결정일: 2026-07-21

상태: **확정**

적용 대상: 신규 리빌드 전체(`apps/`, `packages/` 및 이후 추가되는 신버전 코드)

## 목적

신규 기능, 외부 연동, 기존 기능 보강, 버그 수정이 발생해도 레거시와 같은 함수 덮어쓰기·래퍼 누적·타이머 보정 구조로 돌아가지 않도록 변경 절차와 아키텍처 규칙을 강제한다.

## 1. 모든 변경은 스펙을 거친다

신규 기능, 기능 보강, 연동, 버그 수정, 핫픽스는 다음 절차를 따른다.

1. 요구사항 기록
2. 영향 범위와 데이터 계약 분석
3. Codex 작업 스펙 작성
4. Claude Code의 스펙 범위 구현
5. 자동 테스트와 회귀검증
6. Codex diff 검증
7. 미리보기 배포
8. 필요한 실제 기기 검증
9. 사용자 승인 후 병합·배포

스펙 없는 신버전 코드 변경은 금지한다. 요구가 긴급하다는 이유만으로 이 절차를 생략하지 않는다.

## 2. 함수 덮어쓰기와 후행 패치를 금지한다

다음을 금지한다.

- 같은 이름의 함수·컴포넌트·서비스를 뒤에서 재정의
- 기존 함수를 보관한 뒤 래핑하여 동작 변경
- `window.*` 전역에 신규 상태나 권한 함수 추가
- `V2`, `V3`, `final`, `latest`, `fix`, `new` 접미사로 공식 구현을 병렬 유지
- `<script>` 후행 삽입으로 앞선 구현 교정
- CSS 특이도 경쟁과 무분별한 `!important`로 기존 스타일 덮어쓰기

기능 변경은 해당 기능의 공식 모듈을 직접 수정하고 기존 구현을 교체한다. 과거 구현을 런타임에 함께 유지하지 않는다. 변경 이력은 Git이 담당한다.

## 3. 핵심 동작은 단일 권한만 가진다

아래 동작에는 공식 진입점과 소유 모듈이 각각 하나만 존재해야 한다.

- 관리자 상태 로딩·저장·병합·게시
- 데이터 마이그레이션
- 프레임 렌더링과 인쇄 출력
- 케이스 렌더링과 인쇄 출력
- 룸 렌더링
- 전체화면 상태 전환
- Firebase 인증·Storage·Firestore 접근
- 고객 시안 암·복호화
- 주문 생성·저장·조회

동일 책임의 두 번째 구현이 필요해 보이면 구현 전에 인터페이스, 전략 패턴 또는 기존 모듈 확장으로 해결 가능한지 설계 검토한다.

## 4. 계층 경계를 지킨다

기본 의존 방향은 다음과 같다.

```text
UI → Application service → Domain logic → Repository interface → Infrastructure
```

- UI 컴포넌트에서 Firebase를 직접 호출하지 않는다.
- UI 컴포넌트에 Canvas 렌더링 수학을 넣지 않는다.
- 렌더 엔진에서 브라우저 UI 상태를 직접 변경하지 않는다.
- 도메인 로직에서 localStorage·IndexedDB·Firebase 구현을 직접 참조하지 않는다.
- 저장 구현은 Repository 인터페이스 뒤에 둔다.

순환 의존성은 금지한다.

## 5. 데이터 계약은 버전과 마이그레이션으로 변경한다

영속 데이터에는 명시적인 `schemaVersion`을 둔다.

데이터 필드를 추가·변경·폐기할 때는 다음을 모두 갖춘다.

- 이전 버전을 읽는 마이그레이션 함수
- 반복 실행해도 결과가 같은 멱등성
- 원본 데이터 불변 또는 복구 가능한 백업
- 구버전 fixture 테스트
- 실패 시 중단과 롤백 경로
- 운영 Firebase 쓰기는 별도 승인

새 코드 내부에서는 마이그레이션이 끝난 단일 최신 모델만 사용한다. 화면마다 구버전 필드를 임의 보정하지 않는다.

## 6. 기능 플래그는 임시 전환 장치로만 사용한다

미완성 기능과 단계적 전환은 명시적 기능 플래그로 격리할 수 있다.

각 플래그에는 다음을 기록한다.

- 소유 기능
- 기본값과 환경별 값
- 도입 이유
- 제거 조건
- 제거 예정 작업 번호

안정화가 끝난 플래그와 비활성 코드 경로는 후속 스펙에서 제거한다. 만료 조건 없는 영구 플래그는 금지한다.

## 7. 변경 종류별 필수 테스트

| 변경 종류 | 최소 검증 |
|---|---|
| UI | 컴포넌트 테스트와 주요 화면 시각 비교 |
| 데이터 계약 | 스키마, 마이그레이션, 구버전 fixture |
| 렌더링 | 기준 이미지 비교, 출력 크기, CORS-clean 캔버스 |
| Firebase | Emulator 및 Security Rules 테스트 |
| 전체화면·회전 | 상태 머신 테스트와 실제 모바일 기기 |
| 공유·시안 | 기존 토큰 복호화와 신규 토큰 라운드트립 |
| 주문 | 생성·저장·조회·다운로드 E2E |

버그 수정은 해당 버그를 실패시키는 재현 테스트를 먼저 또는 같은 커밋에 포함해야 한다. 재현 테스트 없이 시간값·지연값만 바꾸는 수정은 승인하지 않는다.

## 8. 패치 누적 경고 신호

다음 중 하나가 새로 발생하면 Claude Code는 구현을 중단하고 스펙에 질문을 남긴다.

- 동일 심볼의 중복 정의
- 기존 함수를 감싸는 래퍼
- 신규 `window.*` 전역
- 초기화 순서를 맞추기 위한 `setTimeout`
- 같은 데이터의 양방향 저장소 덮어쓰기
- 빈 `catch` 또는 오류 무시
- UI·저장·렌더링이 한 모듈에 혼재
- 단일 파일이 여러 도메인 책임을 가짐
- 제거 조건 없는 기능 플래그
- 근거 없는 `!important`
- 공식 구현과 임시 구현의 동시 유지

CI에서 가능한 항목은 정적 검사로 차단한다.

## 9. 핫픽스 규칙

운영 장애 핫픽스도 별도 스펙과 재현 테스트를 가진다. 핫픽스에는 반드시 다음을 기록한다.

- 증상과 영향
- 재현 조건
- 확인된 원인
- 최소 수정 범위
- 롤백 방법
- 임시 우회가 있다면 만료 조건과 제거 작업 번호

원인이 증명되지 않은 보정 코드는 운영 본체에 병합하지 않는다.

## 10. 리뷰 판정

Codex는 구현 diff에서 이 정책 준수 여부를 확인하고 다음 중 하나로 판정한다.

- `승인 가능`
- `수정 후 재검증`
- `재설계 필요`

이 정책을 위반한 변경은 기능이 동작하더라도 승인하지 않는다.
