## 증상 3개와 근본 원인

### ① 화질 깨짐 (blur) — 원인 확정
- **캔버스 백킹이 320×333으로 작음** (뷰포트 891 대비 1/2.8). 여기에 방 사진을 그린 뒤 화면(물리 3120px)에 늘려 = 심한 업스케일 = 블러.
- 설령 제대로 커져도, 삼성 전용 사이저(**V107 rotate-fs 블록**)가 07-06에 백킹을 `cw*dpr`→`cw`로 낮춰(dpr 제거) dpr 3.5에서 흐려짐.
- **결합 함정**: 폭 891 > 861이라 PC용 CSS `#rm-canvas{width:auto!important}`(L13730, `@media(min-width:861px)`)가 **폰에서도 켜짐** → canvas의 표시크기가 백킹크기에 강제로 묶임(그래서 패널 back==css). 사이저의 일반 인라인 `style.width`는 이 규칙에 짐.

### ② 커스텀 스크롤바 안 뜸 — ①과 같은 뿌리
- 스크롤바는 `#rm-canvas-area`에 **세로 넘침이 있을 때만** 표시(`maxScroll = scrollHeight - clientHeight > 2`, 아니면 자동 숨김, L14589).
- 캔버스가 320×333(작음)이라 411 높이에 다 들어감 → 넘침 없음 → **자동 숨김.** 스크롤바 코드는 정상·브라우저 무관.
- **캔버스가 cover(세로로 길게)로 커지면 → 넘침 발생 → 스크롤바 자동 등장.** ①과 동시 해결.

### ③ 가로↔세로 반복 시 액자 스케일 축소 — 메커니즘 확정
- **"방향 전환 시 재적용이 누적된다"는 가설은 코드상 반증됨.** 재적용 블록(L4331, L4381)은 운영자 프리셋에서 읽은 **절대값**을 대입할 뿐 곱하지 않음(프리셋은 별도 키·비변형 → 오염 불가). 두 방향 값 사이를 **진동**할 뿐 래칫 안 됨.
- **진짜 원인 = `RM.__userMoved` 거짓양성 + 읽기/쓰기 비대칭**:
  1. 캔버스 터치 핸들러(`ontouchstart` L2282 / `ontouchmove` L2285–2291)가 **아무 캔버스 터치에나** `RM.dragging=true`, `RM.__userMoved=true`를 세팅.
  2. `__userMoved=true`면 매 렌더의 **운영자 스케일 복원(force) 블록이 꺼짐**(게이트 L4326 `!RM.__userMoved`).
  3. 그 상태로 세로는 `.mobile`(보통 더 작은) 스케일을 슬라이더에 읽어들이고(`dennMergeMobileV` L3461–3463), 소비자 저장은 **항상 base에 씀**(`dennRouteSaveV` L3439, 소비자는 mobile 편집맥락 아님) → 다음 가로가 **줄어든 base**를 읽음(`loadSettingsV33` on rotation L14624).
  4. 결과: `.mobile` 값 쪽으로 **몇 번 줄다가 수렴**(무한 아님). L4381이 되돌릴 수도 있으나 운영자 `guideScale`가 미설정/프리셋 없으면 스킵되어 축소 잔존.
- 개발자도 이미 `a459077` 커밋에서 "미해결 `__userMoved` 거짓양성"으로 플래그.

## ★ 결정적 연결고리 (세 증상을 잇는 핵심)

**스크롤과 스케일 축소는 같은 터치 핸들러로 연결돼 있다.**
- 현재 가로 전체화면 캔버스는 `touch-action:pan-y`(L14408)라 **손가락 세로 스크롤이 이미 허용**됨.
- 그런데 배경을 스크롤하려고 캔버스를 만지면 → `ontouchmove`(L2285–2291)가 **`__userMoved=true`로 오인** → 운영자 복원 꺼짐 → **③ 스케일 축소 발동.**
- 즉 **"배경 스크롤"과 "액자 이동"을 터치 핸들러가 구분 못 하는 것**이 스크롤·스케일 두 문제의 공통 뿌리. → 사용자의 "액자/배경 터치 구분 명확" 직관이 정확히 이 지점을 짚음.

## ⚠️ 미해결 크럭스 (런타임 실측 필요) — 왜 캔버스가 320인가

`320×333`은 core 사이저의 **generic(데스크톱) 분기**에서만 나오는 값(L3946, `rawW=Math.max(320, area.clientWidth-8)`, area≈328px). 이 분기는 **`isRoomMobile()===false`**일 때만 도달.
- 891×411에서 `isRoomMobile` ≈ `matchMedia('(pointer:coarse)')` (폭 891≥760이라 coarse에만 의존).
- **coarse가 삼성서 매칭 안 되면**: `isRoomMobile=false`→generic 320 + `isMob()=false`→회전 핸들러 onChange 조기종료(L14632)하며 `denn-rotate-fs` 제거, 전체화면 사이징 경로 미실행. (핸드오프 A "폭>860 데스크톱 취급"과 동근원.)

**모순**: 스크린샷엔 `rotate-fs`가 **있었다.** coarse-실패 가설이면 없어야 함. → 실제론 **"rmSizeCanvas가 320으로 그린 뒤 클래스가 나중에 붙었고, 이후 재사이징이 rotate-fs 상태로 다시 안 일어남"(stale)** 이라는 뜻. 어느 경로가 이 stale을 만드는지는 **정적 코드만으로 확정 불가.**

### 이 한 가지만 실측하면 못을 박는다
가로 전체화면 상태에서 (콘솔 or ?debug=1 확장 패널):
- `matchMedia('(pointer:coarse)').matches`
- `window.isRoomMobile && isRoomMobile()`
- `document.documentElement.classList.contains('denn-rotate-fs')`
- rmSizeCanvas가 rotate-fs 분기(L3933/L14365)를 실제로 타는지 (임시 카운터)

→ (A) coarse=false면 근본은 **모바일 판정 실패**(사이저가 아니라 detection 문제, 훨씬 상위) / (B) coarse=true인데 320이면 근본은 **재사이징 트리거 누락**(rotate-fs 붙은 뒤 rmSizeCanvas 재실행 안 됨).

## 수정 전략 (삼성 우선, 미구현 — 승인 후)

원칙: **기준 브라우저(삼성) 완벽화 → 카카오 합류.** cover 수학·구도 안 건드림. 회귀 방지 위해 크럭스 실측 후 확정.

1. **화질(①②)**: 크럭스 실측 결과에 따라
   - (A 모바일판정 실패면) 가로 전체화면 판정을 `pointer:coarse`에 의존 않게(클래스/뷰포트 기반) 보정 → 캔버스가 cover 사이징을 타게. → 백킹 커짐 + 넘침 생김(스크롤바 자동).
   - (B 트리거 누락이면) rotate-fs 확정 후 rmSizeCanvas 1회 재실행 보장.
   - 공통: 승리 사이저(V107)의 백킹 `cw`→`cw*dpr` + 표시 `setDisplaySize(...,true)` 인라인 !important로 `width:auto!important` 무력화(선명). ※지난 리팩터링이 깬 건 구도까지 바꿔서였음 — 이번엔 백킹 해상도만.
2. **스크롤 + 스케일 축소(②③)**: 터치 핸들러가 **액자 영역 히트테스트로 "액자 터치 vs 배경 터치"를 구분** → 배경 터치는 스크롤만(‪`__userMoved` 세팅 금지‬), 액자 터치만 이동/`__userMoved`. 이게 ③ 축소를 근절하고 사용자 요청(터치 구분+매끄러운 스크롤)을 동시 충족. 커스텀 스크롤바는 캔버스가 커지면 자동 부활하므로 보조로 유지.
3. **튐**: 사용자 지시대로 **마지막**에.
